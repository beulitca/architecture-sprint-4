# Архитектурное решение по кешированию

## Мотивация
Кеширование может стать хорошим инструментом, чтобы выиграть время до полного редизайна системы. Оно позволит быстро разгрузить критичные ресурсы, уйти от ошибок и прекратить отток клиентов. 

## Данные 

1. Данные заказов MES DB
2. 3d-модели
Опционально:
3. Данные о клиентах в crm 
4. Данные о заказах в shop db в статусах SUBMITTED, MANUFACTURING_STARTED

## Предлагаемое решение

Очевидно, в первую очередь, нужно снизить нагрузку на MES DB и модуль MES API, т к с ними у операторов возникают очевидные проблемы: ускорить чтение данных потребителями в процессе выполнения заказа, сократить число обращений к БД.

1. Redis - MES DB. Паттерн Write Behind или Write Through.

Write Through
Write-though - является самым оптимальным. Если время изменения заказа не критично. Главное – обеспечивать чтение из кэша при проверке, не был ли заказ передан другому оператору. Также следует учитывать, что после изменения статуса данные отправляются в очередь для других систем. 

Write Behind
Это можно сделать с помощью разворачивания Redis кластера с AOF-персистенцией  перед базой Postgre MES.
Один и тот же заказ запрашивается множеством операторов, поэтому имеет смысл выполнить серверное кеширование и размещать заказ в "публичный" кеш, доступный всем операторам. Т к в процессе выполнения заказа, данные о нем востребованы, а статус часто меняется, имеет смысл при записи сразу размещать заказа в кеш и не тратить время на ожидание записи в базу. Т к мы имеем очевидные проблемы с перегрузкой базоы, можно обновлять данные в ней фоново пакетными запросами. На случай перезагрузки сервера Redis для предотвращения потери актуальных данных заказа можно хранить все события изменения заказа с AOF-персистенцией. Программно инвалидировать кеш, когда обработка заказа завершена - статус CLOSED. А также при изменении заказа - Invalidate on Write. Т к заказ находится в кеше только на время обработки, кеш не должен переполниться. Потребителями записей в кеше будет MES API. 
**(В данном случае мы можем только гадать, какие бизнес-процессы реализует система, можно ли переназначать заказа на другого оператора вообще, можно ли дробить заказы по разным операторам? Я исхожу из того, что мы знаем точно - надо разгрузить базу, а значит фоновые батч обновления помогут этого достичь. В решении подразумевается без детализации, что MES-движок проверяет все необходимое, работает с очередью без глубокого анализа use-case-ов, и все делает на основе актуального снепшота в Redis.  Работа шла только с подсвеченными use-case-ами: 1)CRUD по заказам и 2)простое назначение на оператора.)**



2. Redis - S3. Паттерн Refresh-ahead. Тот же Redis кластер можно использовать для серверного кеширования 3d-моделей. Чтение объемного файла занимает время, при назначении заказа файл просматривают разные операторы, а также запросы к хранилищу s3 платные, поэтому лучше держать файлы для активных заказов в кеше. Инвалидировать кеш можно программно при переходе заказа в статус CLOSED. Клиентами кеша могут быть MES API, CRM API, SHOP API. Мы заранее знаем, какие заказы в текущий момент в обработке, поэтому заранее можем разместить документ в кеш согласно паттерну Refresh-ahead.

4. Имеет смысл также реализовать клиентское кеширование 3d-моделей для операторов. Кеш может быть инвалидирован по TTL, например, месяц, т к после регистрации заказа модель не меняется.
5. Имеет смысл также реализовать клиентское кеширование 3d-моделей для розничных клиентов, аналогично.
6. Клиентский кеш заказов в статусе MANUFACTURING_STARTED для клиентов и операторов, т к в этом статусе заказ, определенно, проведет более суток. Или заказа в статусе SUBMITTED на 5 мин, т к рачет стоимости занимает время. Инвалидировать по времени.
7. [Опционально] Локальный кеш в crm api - shop db. Паттерн Write through. Кеш данных о заказе для менеджеров по продажам. Т к менеджеров вряд ли большое число, достаточно кеша в RAM сервера. Также в shop db важно поддерживать актуальные данные для сайта, поэтому используем Write through. Это не увеличить нагрузку на DB при записи, но снизит при чтении. 
4. [Опционально]  Локальный кеш в crm api данных о клиенте. Паттерн Refresh-ahead. Данные клиентов по заказам, находящимся в обработке можно заранее грузить в серверную оперативную память для продажников.
